## hecto-api

Lightweight offline-first desktop API client replacing Postman/Bruno. Wails v2 (Go backend, native webview), Vue 3 frontend, file-based storage (JSON/YAML). Planning in `docs/`, BMad output in `_bmad-output/`.

## Policy

- Never push to main or develop directly; feature branches → MR into develop, develop → merge into main.
- Follow Semantic Versioning for all releases.
- Never hand-edit files under `_bmad-output/` — they are generated by BMad skills.
- Skill directories (`.agent/skills/`, `.agents/skills/`, `.claude/skills/`, `.kiro/skills/`) are gitignored — never commit them.

## Where things are

- Product brief and planning docs: `docs/`
- BMad configuration: `_bmad/config.toml`
- Generated artifacts: `_bmad-output/`

## Running and verifying

- Wails v2: Run `wails dev -tags webkit2_41` in the `projects` directory to start the development server. Requires Go 1.25.0.
- Vue 3 frontend: Dev server is managed by Wails, but you can run bun scripts from `projects/frontend/package.json` if needed.
- Node version: 24 (`.nvmrc`).

## Epic 2 UI Smoke Test Checklist

When testing Epic 2 features visually, verify the following:
- Collection tree loads and displays folders/requests correctly.
- Creating a new request/folder adds it to the tree immediately.
- Selecting a request loads its details into the editor (URL, method, empty state).
- Renaming a request/folder updates the tree instantly.
- Deleting a request/folder removes it from the tree and clears the editor if it was selected.
- Duplicating a request creates a copy (e.g., "Copy of ...") in the tree.
- Modifying a request shows an amber unsaved changes dot in the context menu.


## Conventions that differ from defaults

- Storage is always file-based JSON/YAML on disk — no database, no cloud sync, no login.
- Money-style numeric values (response time, size) use integers, not floats.

## Tooling (frontend)

- Package manager is **bun** (see `projects/wails.json`, `projects/frontend/bun.lock`). Always use `bun install` / `bun run <script>` — never `npm`, `npx`, `yarn`, or `pnpm`, even if a spec says `npm run ...`.
- Shell default Node is v18, but the project needs Node 24 (`.nvmrc`). Before running any frontend/Node/bun/wails command, run `source ~/.nvm/nvm.sh && nvm use` in the project root (in the same shell invocation as the command).

## Git rules (OVERRIDES policy above)

- **Branching**: Story work (`/bmad-build`) is done DIRECTLY on the `develop` branch. Do NOT create feature branches. Do NOT ask the user which branch to use. Ignore the "Never push to develop" policy for story work.
- **Safety**: Never run `git commit`, `git push`, or any version-control write operation without explicit user approval. Always ask first.
- **Skill Tracking**: Các thư mục skill (`.agent/skills/`, `.agents/skills/`, `.claude/skills/`, `.kiro/skills/`) được commit và track trong Git (đã gỡ khỏi `.gitignore`).

## Release, Versioning & Commit Squashing

- **Single Source of Truth cho Version**:
  - Toàn bộ ứng dụng và các script đóng gói (`projects/build-dmg.sh`, `projects/build-deb.sh`,...) BẮT BUỘC lấy version từ `projects/frontend/package.json`. Tuyệt đối không hardcode version ở từng script riêng rẽ.
  - Giao diện UI (`AppHeader.vue`) import trực tiếp version từ `package.json`.
- **Semantic Versioning**:
  - Tuân thủ SemVer (MAJOR.MINOR.PATCH):
    - Thêm tính năng mới tương thích ngược -> tăng MINOR (ví dụ: `1.0.0` -> `1.1.0`).
    - Sửa lỗi -> tăng PATCH (ví dụ: `1.1.0` -> `1.1.1`).
    - Thay đổi phá vỡ tương thích (breaking changes) -> tăng MAJOR.
- **Quy trình gom và chuẩn hóa commit khi chốt tính năng**:
  - Khi hoàn thành chốt một đợt tính năng / milestone:
    1. Cập nhật version mới trong `projects/frontend/package.json`.
    2. Chạy kiểm tra toàn diện (`bun run type-check`, `bun run test`, `go test ./...`) đảm bảo pass 100%.
    3. Tiến hành gom (squash) toàn bộ các commit lẻ trên nhánh `develop` tính từ commit chuẩn gần nhất (`v1.x.x`) thành 1 commit duy nhất chuẩn hóa: **Tiêu đề BẮT BUỘC chỉ là `v<version>`** (ví dụ: `v1.2.0`, `v1.1.0`), phần thân là danh sách bullet points thay đổi. Tuyệt đối không dùng prefix `feat: release ...`.
    4. **Push & Tạo MR vào `main`**: Push force nhánh `develop` và tự động tạo Merge Request vào `main` qua Git push options (`git push -o merge_request.create -o merge_request.target=main -o merge_request.title="v<version>" origin develop --force`).
    5. **MANDATORY CONFIRMATION**: Luôn trình bày tóm tắt thay đổi và xin xác nhận của người dùng trước khi chạy các lệnh `git commit`, `git reset`, `git push`. (Ngoại lệ: xem Quy trình Build Fix sau Release bên dưới).
- **Quy trình Build Fix sau Release (Tự động hóa)**:
  - Khi pipeline CI bị fail sau release hoặc cần fix nóng cho bản release hiện tại:
    - Tiêu đề commit chuẩn hóa: `v<version> (build <n>)` (với `n` tự tăng dần: `v1.3.0 (build 1)`, `v1.3.0 (build 2)`,...).
    - **Ngoại lệ xác nhận:** Khi người dùng gửi log lỗi build/CI của bản release hoặc yêu cầu fix build, agent tự động sửa lỗi, chạy kiểm thử xác nhận pass 100%, tự động commit `v<version> (build <n>)` và push lên `develop` mà không cần hỏi lại xác nhận.
- **Wails Binding Model Tracking**:
  - Thư mục `projects/frontend/wailsjs/` BẮT BUỘC phải được commit và theo dõi trong Git (tuyệt đối không thêm vào `.gitignore`), vì môi trường CI chỉ chạy trên container Node/Bun không có Wails CLI để generate bindings.

## Review gate (bmad-build)

**Purpose:** The gate between step-03 (implement) and step-04 (review) exists so the human can switch to a different model before review. Review is still performed by the agent (via review subagents, step-04) — NOT by the human. The gate is a pause, not a hand-off of the review work.

- **MANDATORY HALT**: After step-03 finishes and verification passes, you MUST:
  1. Set sprint-status to `review` (spec `in-review`).
  2. Tell the human the story is at the review gate and they can switch model.
  3. **STOP / HALT**. Do NOT start step-04 in the same turn. NEVER self-review inline and mark as done in the same turn.
  *(Exception: For unattended `bmad-build-auto` runs, skip this gate and proceed directly to step-04.)*
- **Resuming**: When the human resumes and tells you to proceed, run step-04 using **subagents** (if available, otherwise run the reviews directly in the same session). Run the three review layers (blind-hunter, edge-case-hunter, verification-gap) concurrently, triage findings, and apply patches.
- Never set the spec to `done` until review findings are triaged.
